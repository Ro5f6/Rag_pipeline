Agentic RAG and Iterative Retrieval

Standard RAG retrieves once and generates once. Agentic RAG lets the model decide whether to retrieve, what to retrieve, and how many times, treating retrieval as a tool call rather than a fixed pipeline stage.

The motivation is that a single retrieval pass cannot answer multi-hop questions. Asking which database the team behind a specific service migrated to requires first finding the team, then finding the migration decision. One embedding of the whole question matches neither passage well, because no single passage contains both facts.

An agent loop addresses this by alternating reasoning and retrieval. The model examines the question, issues a search, reads the result, decides whether it has enough information, and searches again with a refined query if it does not. This is the ReAct pattern of interleaved reasoning and acting.

Query routing is a lighter-weight variant. Rather than a full loop, a classifier decides which knowledge base or tool a question should go to, sending product questions to documentation and account questions to a database. This captures much of the benefit at a fraction of the latency.

Self-correction adds a verification step where the model grades whether retrieved passages are actually relevant before using them, and retries with a different query when they are not. This helps most on queries where retrieval reliably fails in a detectable way.

The costs are substantial and often understated. Each loop iteration adds a full model call plus a retrieval round trip, so latency and token spend grow linearly with iterations. Loops can fail to terminate, requiring hard iteration caps. Debugging becomes much harder because the execution path differs per request, which makes tracing every step mandatory rather than optional.

The engineering judgment is to start with single-pass retrieval, measure where it fails, and add agentic behaviour only for the query classes that demonstrably need it. Multi-hop questions justify a loop; the majority of factual lookups do not, and paying loop latency on every request to serve a minority of queries is a poor trade.
